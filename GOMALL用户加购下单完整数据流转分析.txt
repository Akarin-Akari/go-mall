 ┌─────────────────────────────────────────────────────────────────────────────────┐
 │               前端加购数据流转        │

 │                │
 │ 用户点击"加入购物车"        │
 │    ││

 │ ┌──────────────────────────────────────┐                   │
 │ │ 页面组件 (products/[id]/page.tsx)  │                   │

 2. 后端下单流程

 ┌─────────────────────────────────────────────────────────────────────────────────┐
 │               后端下单数据流转                   │

 │    │                                   │
 │    ▼                                   │

 │ │ Handler层 (handler/order/order.go) │                   │

 │    ││

 │ │ ┌────────────────────────────────────────────────────────────────────┐ │ │

 三、并发控制与安全机制

 ┌─────────────────────────────────────────────────────────────────────────────────┐
 │             并发控制与安全机制总览│
 ├─────────────────────────────────────────────────────────────────────────────────┤
 │                                        │
 │ ┌───────────────────────────────────────────────────────────────────────────┐ │
 │ │ 1. 购物车加购- 分布式锁        │ │
 │ │  位置: pkg/cart/cache_service.go                    │ │
 │ │  机制: Redis SetNX (SETNX key value EX timeout)            │ │
 │ │  锁键: cart:lock:{userID}:{sessionID}                 │ │
 │ │  超时: 10秒                               │ │
 │ │  作用: 防止同一用户并发加购导致数量计算错误                │ │
 │ └───────────────────────────────────────────────────────────────────────────┘ │
 │                                        │
 │ ┌───────────────────────────────────────────────────────────────────────────┐ │
 │ │ 2. 订单创建 - 订单锁                            │ │
 │ │  位置: pkg/order/cache_service.go        │ │
 │ │  机制: Redis SetNX│ │
 │ │  锁键: order:lock:{userID}                       │ │
 │ │  作用: 防止用户重复点击提交订单                │ │
 │ └───────────────────────────────────────────────────────────────────────────┘ │
 │                                        │
 │ ┌───────────────────────────────────────────────────────────────────────────┐ │
 │ │ 3. 库存扣减 - 乐观锁                            │ │
 │ │  位置: pkg/order/order_service.go        │ │
 │ │  机制: SQL WHERE条件                          │ │
 │ │  SQL: UPDATE products SET stock = stock - ?│ │
 │ │    WHERE id = ? AND stock >= ?                │ │
 │ │  作用: 防止超卖，保证库存不为负                      │ │
 │ └───────────────────────────────────────────────────────────────────────────┘ │
 │        │
 │ ┌───────────────────────────────────────────────────────────────────────────┐ │
 │ │ 4. 订单创建 - 短事务设计                          │ │
 │ │  位置: pkg/order/order_service.go                   │ │
 │ │  策略:│ │
 │ │  - 库存扣减在独立事务中完成（第二步）                   │ │
 │ │  - 订单创建在短事务中完成（第三步）                    │ │
 │ │  - 避免长事务锁表│ │
 │ └───────────────────────────────────────────────────────────────────────────┘ │
 │                                        │
 │ ┌───────────────────────────────────────────────────────────────────────────┐ │
 │ │ 5. 缓存一致性                               │ │
 │ │  位置: pkg/cart/cache_service.go, pkg/order/cache_service.go      │ │
 │ │  策略: 写后清除缓存 (Cache Aside Pattern)                │ │
 │ │  - 加购后清除购物车缓存                        │ │
 │ │  - 下单后清除购物车和订单缓存│ │
 │ └───────────────────────────────────────────────────────────────────────────┘ │
 │ │
 └─────────────────────────────────────────────────────────────────────────────────┘

 ├─────────────────────────────────────────────────────────────────────────────────────┤
 │        │
 │ ╔═══════════════════════════════════════════════════════════════════════════════╗ │

 │    ▼                                     │

 ││
 │    ││
 │    ▼                                     │
 │ [Handler] CartHandler.AddToCart()                │
 │    ││
 │    ▼ (检查cacheService是否存在)                        │
 │ [Cache] CacheService.AddToCartWithCache()                     │
 │    │├── acquireLock()获取分布式锁                      │
 │    │ ├── cartService.AddToCart() 调用核心服务                │
 │    │ ├── clearCartCache() 清除缓存                      │
 │    │ └── releaseLock() 释放锁                         │
 │    ▼│
 │ [Service] CartService.AddToCart()                         │
 │    │ ├── 验证商品 (Product表查询)                       │
 │    │ ├── 验证SKU (ProductSKU表查询)                      │
 │    │ ├── 检查库存        │
 │    │ ├── getOrCreateCart() 获取/创建购物车                   │
 │    │ ├── 查找/创建 CartItem        │
 │    │ └── updateCartSummary() 更新购物车统计                  │
 │    ▼                                     │
 │ [Model] Cart, CartItem ──── GORM操作 ────► [DB] SQLite/MySQL           │
 │  │
 │ ═══════════════════════════════════════════════════════════════════════════════│
 │        │
 │ ╔═══════════════════════════════════════════════════════════════════════════════╗ │
 │ ║               下单流程                     ║ │
 │ ╚═══════════════════════════════════════════════════════════════════════════════╝ │
 │                                          │

 │    │ └── 同步购物车项到后端                        │
 │    ▼                                     │
 │ [Redux] orderSlice.createOrderAsync()                       │
 │    │                             │
 │    ▼                                     │
 │ [API] orderAPI.createOrder() ──── POST /api/orders────►             │
 │                                          │
 │    │                                     │
 │    ▼│
 │ [Handler] OrderHandler.CreateOrder()                       │
 │    │ ├── 解析请求参数│

 │    │                                     │
 │    ├──► Step1: 查询 CartItem + Preload Product/SKU        │

## 二、当前链路里最值得警惕的 6 个风险点（电商常见坑）

### ⚠️ 1) Redis 分布式锁的“安全释放”问题

你写的是 `SetNX + EX timeout`，但如果解锁时直接 `DEL key`，会有经典风险：

* A 拿锁（key=A, ttl=10s）
* A 执行慢，ttl 到期
* B 拿到新锁（key=B）
* A 终于执行完，`DEL key` 把 B 的锁删了 → **并发保护失效**

✅ 必须用 **value 校验 + Lua 原子释放**（只删自己的锁）。

---

### ⚠️ 2) “扣库存独立事务”带来的跨步骤一致性

你当前步骤是：

1. 查购物车项并验证
2. 扣库存（独立事务）
3. 短事务创建订单 + 删除购物车项

风险在于：**2 成功但 3 失败**时会出现：

* 库存被扣了
* 订单没创建出来
* 购物车可能还在
  → 需要补偿或可重试设计

✅ 两种成熟做法（二选一）：

* **做补偿**：订单创建失败 → 把库存加回去（需要幂等/重试安全）
* **做“冻结库存”**：下单先冻结，支付成功再扣减（更电商）

### ⚠️ 3) 购物车项的“价格快照”与“下单金额计算”一致性

* 商品改价后，用户仍按老价下单（可能不符合业务）
  如果用商品表现价计算，会有：
* 购物车展示价和下单价不一致（用户投诉）

✅ 建议明确策略（强烈建议写进业务规则）：

* **下单时重新计算价格**（以商品当前价/活动价为准），并在响应里返回“价格变动提示”
* 或者允许“购物车价锁定 X 分钟”（配合冻结价/活动）

✅ 推荐：

### ⚠️ 5) Preload Product/SKU 的读一致性与性能

高并发结算时，`Preload` 很容易把事务拖长、造成 N+1 或锁等待（特别 MySQL）。

✅ 建议：

### ⚠️ 6) 缓存一致性：删缓存 ≠ 一致

### 🚨 Critical Risk: 这个“坑”如果不填，就要背锅了！

阿卡林，请注意看你的 **下单流程 - 后端 Step 2 和 Step 3**：

```text
Step 2: 扣减库存（独立事务）
Step 3: 创建订单（短事务，如果失败回滚）

```

**这里有一个巨大的 Consistency Gap (整合性ギャップ)！⚠️**

* **Scenario (场景推演):**
1. **Step 2 成功:** Redis/DB 扣减库存成功 (Stock: 10 -> 9)。
2. **Network Issue / Database Crash:** 在进入 Step 3 之前，或者 Step 3 执行过程中，服务器突然 **宕机 (Crash)** 或者抛出了 Panic。
3. **Result:** 因为 Step 2 是“独立事务”，它已经提交了。但是 Step 3 失败了，订单没有创建。
4. **Outcome:** **库存丢了！** (Stock lost)。用户没看到订单，但是商品库存却被扣掉了。这就是所谓的 **"Phantom Stock" (幽灵库存)** 现象。



**Fix Proposal (修正案):**

在 Monolithic (单体) 架构或者简单的微服务架构中，为了保证 **ACID**，通常有这种做法：

1. **强一致性 (Strong Consistency):** 把 Step 2 和 Step 3 放进**同一个数据库事务 (Transaction)** 里。
* *Pros:* 绝对安全，同生共死。
* *Cons:* 锁表时间变长。但在 Mall-Go 这个阶段，性能瓶颈通常不在 DB 事务时长上，而在网络 IO 上。这是最推荐的 MVP 做法。


2. **最终一致性 (Eventual Consistency):** 如果非要拆分，Step 3 失败时，必须必须必须要有一个 **Compensating Transaction (补偿事务)** —— 即自动把库存加回去。

### 💡 Optimization: 真正的“防抖”与幂等 (True Idempotency)

你提到了 `order:lock:{userID}` 来防止重复提交。

* **Issue:** 如果用户在电梯里，网络极差。他点了提交，请求发出了，后端处理完了（订单创建成功），但是 **Response 没能返回给前端**。
* **User Action:** 用户以为没点上，又狂点了一次。
* **Result:** `order:lock` 早就释放了（因为上次请求处理完了），于是后端又创建了一个**一模一样**的订单。用户买了双份！😱
* **Solution:** **Idempotency Key (冪等性キー)**
1. **前端:** 进入“结算页”时，生成一个唯一的 UUID (e.g., `order_token`).
2. **提交时:** 把这个 Token 发给后端。
3. **后端:** 检查 Redis `exists order_token:{uuid}`。
* 如果存在，说明已经处理过，直接返回上次的 Order ID。
* 如果不存在，执行下单，并 set 这个 key。
