  ├─────────────────────────────────────────────────────────────────────────────────┤
  │ func (h *Handler) Login(c *gin.Context) {                │
  │     // 1️⃣ 参数绑定                │
  │     var req model.UserLoginRequest                                              │
  │     if err := c.ShouldBindJSON(&req); err != nil {                              │
  │         response.BadRequest(c, "请求参数错误")│
  │         return│
  │     }│
  │                                                                                 │
  │     // 2️⃣ 查找用户                                                               │
  │     var user model.User│
  │     if err := h.db.Where("username = ?", req.Username).First(&user).Error;│
  │        err != nil {                                                             │
  │         response.Unauthorized(c, "用户名或密码错误")// 不暴露用户是否存在         │
  │         return│
  │     }│
  │                                                                                 │
  │     // 3️⃣ 检查用户状态                                                           │
  │     if !user.CanLogin() {                                                       │
  │         if user.IsLocked() {                                                    │
  │             response.Unauthorized(c, "账户已被锁定，请稍后再试")                   │
  │             return                                                              │
  │         }                │
  │         response.Unauthorized(c, "账户状态异常，无法登录")                │
  │         return│
  │     }│
  │                                                                                 │
  │     // 4️⃣ 验证密码                                │
  │     if !user.CheckPassword(req.Password) {                                      │
  │         user.IncrementLoginAttempts()// 增加失败计数                           │
  │         h.db.Save(&user)// 保存状态                               │
  │         response.Unauthorized(c, "用户名或密码错误")                              │
  │         return                                                                  │
  │     }                                                                           │
  │                                                                                 │
  │     // 5️⃣ 登录成功处理                                                           │
  │     user.ResetLoginAttempts()          // 重置失败计数                           │
  │     user.UpdateLastLogin()             // 更新最后登录时间                        │
  │     h.db.Save(&user)                │
  │                │
  │     // 6️⃣ 生成JWT令牌│
  │     token, err := auth.GenerateToken(user.ID, user.Username, user.Role)         │
  │     if err != nil {                                                             │
  │         response.ServerError(c, "登录失败，请稍后重试")                            │
  │         return│
  │     }│
  │                                                                                 │
  │     // 7️⃣ 返回登录数据                                                           │
  │     loginData := map[string]interface{}{                                        │
  │         "token":      token,                                                    │
  │         "expires_in": 86400,           // 24小时                                 │
  │         "user":user.ToResponse(),                                        │
  │     }                                                                           │
  │     response.Success(c, "登录成功", loginData)                                   │
  │ }│

### 💡 Potential Improvements: 还可以更“变态”一点 (Optimization)

虽然现在的流程已经可以跑通 MVP (Minimum Viable Product)，但如果我们考虑到**高并发 (High Concurrency)** 或者更严格的安全审计，这里有几个 **Gap** 可以填补：

#### 1. 登录失败锁定的“坑” (The Trap of Login Locking)

你现在的逻辑是：

```go
// User struct
LoginAttempts int `gorm:"default:0"`

```

* **Issue:** 这种把失败次数写进 SQL 数据库的做法，在低并发下没问题。但是！如果此时有大量请求同时打进来（比如 Distributed DDoS），数据库的 I/O 会成为**瓶颈 (Bottleneck)**。而且，如果之后 Mall-Go 扩展成微服务，数据库压力会巨大。
* **Solution (ソリューション):** 建议使用 **Redis** 来做计数器。
* Key: `login_fail:{username}`
* Value: 失败次数
* TTL: 30分钟
* **Benefit:** Redis 的原子操作 `INCR` 极其快，且不会锁表。



#### 2. Token 的“续命”问题 (Token Rotation)

你在“安全机制一览表”里提到了 Refresh Token，但在流程图中主要展示了 Access Token。

* **Concept:** **Sliding Window (滑动窗口)** 机制。
* **Scenario:** 现在的设置是 24小时过期。如果用户在第 23小时 59分 正在下单，第 24小时 01分 突然 Token 失效跳回登录页，用户绝对会**暴走 (Rage Quit)**。
* **Implementation:** 在中间件里，如果检测到 Token 即将过期（比如剩余时间 < 1小时），自动颁发一个新的 Token 放在 Response Header 里，前端拦截器自动替换本地 Token。

#### 3. 密码哈希的 Cost

```go
const DefaultCost = 12

```

* **Trade-off:** `bcrypt` 的 cost 越高，CPU 计算越慢，安全性越高。Cost 12 是一个不错的平衡点（大约几百毫秒）。但要注意，如果你的服务器 CPU 较弱，大量并发注册可能会导致 CPU 飙升到 100%。可以根据实际服务器 benchmark 调整这个值（10-12 都是 range 内）。
