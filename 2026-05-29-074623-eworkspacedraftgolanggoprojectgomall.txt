     ---
     二、确认存在的 7 个改进点（按优先级）

     🔴 P0-1 订单创建无幂等键（最严重）

     现状：internal/handler/order/order.go:287-313 CreateOrder 只用
     AcquireOrderLock(userID) 做防抖。锁在 defer ReleaseOrderLock
     时立刻释放——一旦请求成功返回但网络抖动让前端没收到
     response，用户重试时锁已释放，会创建第二个一模一样的订单（gemini3
     的"双倍订单"场景）。

     改造：
     - 新增 internal/model/order.go Order 表加字段 IdempotencyKey string 
     gorm:"size:64;uniqueIndex"`
     - internal/handler/order/order.go:287 CreateOrder 入口读 Idempotency-Key
     header（或 body idempotency_key 字段）
     - 在 pkg/order/order_service.go:34 CreateOrder 开头先 SELECT * FROM orders 
     WHERE idempotency_key=?，命中直接返回旧订单；未命中创建时把 key 写入。利用
     DB unique index 兜底并发。
     - 前端 checkout 进入页面时本地生成 UUID 作为 key，提交时随 body 发上来。

     验证：写一个并发测试，同时发 5 个相同 key 的请求，只应创建 1 个订单。

     ---
     🔴 P0-2 下单删购物车项缺归属校验（越权风险）

     现状：pkg/order/order_service.go:87 直接 tx.Where("id IN ?", 
     req.CartItemIDs).Delete(&model.CartItem{})——没有 cart_id = ? 或 user_id = ?
     约束。虽然 line 46-52 查询时按 cart_id 限定了，但若 req.CartItemIDs 
     里掺杂了别人的 ID（查询会被 Preload 
     过滤），删除环节没有二次过滤。理论上当前不会越权删除（因为 cartItems 是按
     cart_id 查回来的），但语义不严谨，未来重构易引入 bug。

     改造：
     - pkg/order/order_service.go:87 改为 tx.Where("id IN ? AND cart_id = ?", 
     req.CartItemIDs, userCart.ID).Delete(&model.CartItem{})
     - 并在第 51 行查询后增加断言：if len(cartItems) != len(req.CartItemIDs) { 
     return errors.New("部分购物车项不存在或不属于当前用户") }（防止 CartItemIDs
     里有越权 ID 被静默丢弃）

     ---
     🟡 P1-3 注册接口未捕获 DB unique 冲突

     现状：pkg/user/register_service.go:85-106 先 SELECT COUNT 检查
     username/email/phone，Model 有 uniqueIndex，但 db.Create 报错时只返回
     "创建用户失败"，未区分 gorm.ErrDuplicatedKey。并发注册下两个请求都过 SELECT
     检查后双双 INSERT，第二个会撞 DB 约束。

     改造：
     - pkg/user/register_service.go:158 附近 Create 之后 errors.Is(err, 
     gorm.ErrDuplicatedKey) → 返回 "用户名或邮箱已被使用"。

     ---
     🟡 P1-4 自动关单未挂定时器（库存被占住）

     现状：pkg/recovery/error_recovery.go:236 cancelExpiredOrder 逻辑存在但属于
     ErrorRecoveryService 的恢复任务，要靠手工 CreateRecoveryTask
     触发；InitGlobalErrorRecoveryService:397 只有 go ProcessRecoveryTasks()
     处理已派发任务，没有定时扫描 orders WHERE status='pending' AND 
     pay_expire_time < NOW() 的 cron。结果：用户下单 → 扣库存 → 不支付 →
     订单永远 pending → 库存永远占着。

     改造：
     - 新建 pkg/order/scheduler.go，启 goroutine + time.Ticker(1*time.Minute)
     扫描超时订单
     - 调用 statusService.UpdateOrderStatus(orderID, OrderStatusClosed, ...)
     并调 inventoryService.RestoreStock 把库存还回去
     - 在 cmd/server/main.go（或当前的启动入口）启动时拉起该 scheduler

     ---
     🟡 P1-5 登录锁定响应缺 retry_after

     现状：pkg/user/login_service.go:102 锁定时只回 error message
     "账户已锁定"；前端无法做倒计时 UX。

     改造：
     - internal/model/user.go LoginResponse 加 LockedUntil *time.Time +
     RetryAfter int64（秒）
     - pkg/user/login_service.go:41-102 检测到 user.IsLocked() 时填充返回值
     - 同时把锁定计数从纯 DB 字段迁移到 Redis INCR + TTL（解决 gemini3 的 DB I/O
     瓶颈）：
       - Key: login_fail:{username} Value: 次数 TTL: 30min
       - 5 次后写 login_lock:{username} 标记锁定
       - 保留 DB LoginAttempts 仅作长期审计用

     ---
     🟡 P1-6 敏感操作审计日志缺失

     现状：UserLoginLog 只记登录。密码修改 / 邮箱变更 / 角色变更 / Token 刷新 /
     锁定解锁 这些操作没有审计表。

     改造：
     - 新建 internal/model/audit_log.go：AuditLog{UserID, Action, TargetType, 
     TargetID, IP, UserAgent, OldValue, NewValue, CreatedAt}
     - 新建 pkg/audit/audit_service.go 提供 Log(ctx, action, ...) 接口
     - 在 pkg/user/ 各 service
     的敏感操作点（ChangePassword、ChangeEmail、AssignRole 等）调用一次

     ---
     🟢 P2-7 JWT Claims 增加 SessionID/DeviceID

     现状：pkg/auth/jwt.go:13-18 Claims 只有 UserID/Username/Role。LoginRequest
     收了 DeviceID 但没塞进 JWT。无法做单设备登录、异地踢人、Session 黑名单。

     改造：
     - pkg/auth/jwt.go Claims 加 SessionID string + DeviceID string
     - 登录时生成 SessionID（UUID）存 Redis session:{sessionID} → userID，TTL =
     JWT 过期时间
     - AuthMiddleware 解析 Token 后多一步 redis.EXISTS 
     session:{sessionID}，被踢出的 session 直接 401
     - 后台接口 POST /api/users/sessions/revoke 删 Redis key 即可踢人
